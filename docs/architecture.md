# Arquitectura

Cómo está organizado el código de ARCLI y dónde tocar para extenderlo. Pensado para contributors; para usar el CLI no hace falta.

Stack: TypeScript estricto (ESM), Node.js, [commander](https://github.com/tj/commander.js), [zod](https://zod.dev), [`@arcasdk/core`](https://github.com/ralcorta/arcasdk) para hablar con ARCA, `conf` para la configuración persistente y `@inquirer` para el modo interactivo.

## Flujo de una emisión

```text
src/cli (commander)
  -> parseo de flags y carga del JSON (--cargar)
  -> src/modules/billing: mezcla flags > JSON > config > defaults, valida, arma la solicitud
  -> src/services/arca: gateway contra ARCA (emite con --emitir; la vista previa también consulta: padrón, cotización, tablas de WSFEX)
  -> src/modules/pdf + src/services/pdf: PDF opcional, después de emitir
  -> presenter del módulo (billing.presenter.ts) con los paneles de src/ui (o JSON)
```

Entre el parseo y la vista previa, `prepareBillingInput` (`src/modules/billing/billing.prepare.ts`) completa la condición IVA desde el padrón, pide la cotización oficial si hace falta y junta los avisos de la entrada. La usan los comandos con flags y el modo interactivo, así que los dos preparan la emisión igual. El régimen FCE se consulta aparte, con el lote ya validado (`resolveFceWarningsInOrder`). `executeBillingCommand` recibe la config y los gateways como dependencias, para testear el comando entero con un ARCA falso (`billing.command.execute.test.ts`).

La factura de exportación `E` y sus notas recorren el mismo camino con otro módulo y otro gateway: `src/modules/export` (mezcla, validación de ítems y armado del `Cmp` de WSFEX) y `src/services/arca/arca-export.gateway.ts` (`wsfex`), porque WSFEX tiene otro contrato que `wsfe`.

El comportamiento visible de cada paso está en el [modelo mental](mental-model.md).

| `src/lib/`                  | Utilidades puras: fechas argentinas, errores de la app, lectura de JSON, rutas enmascaradas, validación de PEM y certificados.                                                                                                                                                                                                                                                                                                                                                                                                                                    |

Reglas de dependencia:

- La lógica de negocio vive en `modules/`, nunca en `cli/`.
- Solo `services/` conoce `@arcasdk/core`. El resto importa los tipos del SDK de `src/services/arca/arca-sdk.types.ts`, el único archivo que puede usar una ruta interna (`@arcasdk/core/lib/...`): la raíz del SDK no exporta los tipos del comprobante de wsfe, y si una versión los mueve se arregla ahí.
- `src/ui` no importa `modules`, `services` ni `cli`. Lo que depende del dominio, como las etiquetas de los campos en un error de zod, lo describe el módulo y `cli` lo une (`formatCliError` en `cli/error-output.ts`).
- `lib`, `modules` y `services` importan la UI desde sus barrels (`ui/primitives`, `ui/components`, `ui/presenters`, `ui/stream`, `ui/theme`), nunca desde `src/ui`: ese barrel reexporta todo y arma ciclos. `cli` puede usar `src/ui`. Dentro de `src/ui`, imports directos entre archivos.
- ESLint (`no-restricted-imports`) hace cumplir las tres reglas anteriores.

## El plugin de PDF

`@arcasdk/pdf` renderiza con Puppeteer y descarga un navegador, así que **no es dependencia de ARCLI**. Se instala con `npm install --ignore-scripts` en `<carpeta de config>/plugins/pdf` y se carga con `createRequire` (`src/services/pdf/pdf-plugin.ts`). ARCLI fija una versión del plugin; si cambia, `arcli pdf` lo avisa. Comportamiento para usuarios: [PDF de comprobantes](pdf.md).

## Cómo extender

### Agregar un comprobante

Dentro del alcance del proyecto (A, B y C de factura, nota de crédito y débito, sus versiones FCE y Recibo A, B y C):

1. Definilo en `src/modules/billing/voucher-kind-map.ts` (`VOUCHER_KIND_MAP`): tipo ARCA, familia, letra y si requiere comprobante asociado.
2. Los comandos se registran solos desde ese mapa (`registerBillingShortcutCommands` y `registerBillingFamilyCommands`).
3. Si cambia una regla de negocio, ajustala en `src/modules/billing/`.
4. Actualizá tests y docs ([cli-reference](cli-reference.md), [validation-rules](validation-rules.md)).

La letra `E` no pasa por `VOUCHER_KIND_MAP`: WSFEX tiene otro contrato (autorización que no lanza, ítems, país de destino, tablas propias), así que vive en `src/modules/export/` con sus propios tipos (`EXPORT_VOUCHER_KIND`, `EXPORT_CREDIT_NOTE_KIND`, `EXPORT_DEBIT_NOTE_KIND`) y su gateway. Las notas `E` consultan su asociado con `FEXGetCMP` (`ExportGateway.getVoucher`, una lectura) antes de armar el `Cmp`: toman de ahí cliente, destino y moneda, y lo comparan con las reglas que ARCA aplica contra el asociado (`src/modules/export/export.notes.ts`). A diferencia de `FEXGetLast_CMP`, `FEXGetCMP` lleva el `Cmp` fuera de `Auth`, así que el SDK no lo rompe.

### Agregar una clave de configuración

1. Sumala a `configPublicKeySchema` y al esquema en `src/modules/config/config.schemas.ts`.
2. Mapeala en `ConfigService` (`config.service.ts`) y validala en `config-value-parser.ts`.
3. Ubicala en una sección y ponele nombre en `config.sections.ts`: de ahí salen el orden de `arcli config` y de "Modificar configuración" (un test exige que cada clave esté en una sola sección). Agregá cómo se muestra su valor en `config.presenter.ts`.
4. Documentala en [configuración](configuration.md) y, si el modo interactivo la expone, en `src/modules/interactive/config-fields.ts`.

### Cambiar el contrato

Comandos, flags, claves de config y JSON son contrato público. Antes de cambiarlos, mirá [CONTRIBUTING](../CONTRIBUTING.md#contrato-del-cli) y actualizá [entrada y salida](input-output.md) y los tests de serialización.

## Decisiones de diseño

- **Docs con una sola fuente.** El sitio (`site/`, Starlight) genera sus páginas desde `docs/` en cada build en vez de mover los archivos: los links de GitHub que ya circulan siguen andando, los tests de docs leen lo mismo y nadie edita dos copias. Ver [Sitio de documentación](development.md#sitio-de-documentación).
- **Una página por comprobante, generada.** Las opciones de cada comprobante se repiten mucho entre páginas (monto, concepto, receptor, al ejecutar). `scripts/docs/comprobantes.ts` las tiene una sola vez, con su largo, su corto y qué es, y la lista de cada comprobante; las condiciones IVA por letra salen de `listAllowedIvaConditions`. `yarn docs:comprobantes` escribe `docs/comprobantes/*.md` (tablas que se leen en GitHub) y el sitio dibuja cada opción como tarjeta con los comentarios `<!-- arcli: ... -->`. `scripts/docs/comprobantes-docs.test.ts` falla si los `.md` quedaron viejos, si un flag del CLI no está o si se nombra uno que no existe. Se descartó leer los textos de la ayuda de commander: son para la terminal y no explican cada valor.
- **Íconos del README, del sitio.** Los títulos `##` del README llevan los dibujos de `site/src/icons.ts` como SVG sueltos en `docs/assets/iconos/` (GitHub no deja SVG en línea ni `style`), con trazo celeste `#2f86c9` fijo, que se ve sobre el fondo claro y el oscuro de GitHub. `yarn docs:readme-iconos` los escribe y pone cada título con su `<img>` y un `<a id>` con el ancla de antes (con el ícono, GitHub generaría `#-empezar`); `scripts/docs/readme-iconos.test.ts` falla si se desincronizan. El sitio no publica el README, así que no le llegan los `<img>`.

- **Consultar antes que copiar.** Una regla de ARCA copiada en ARCLI queda vieja en silencio: si ARCA la afloja, ARCLI sigue bloqueando algo válido. Cuando ARCA tiene un método de consulta, la vista previa le pregunta en lugar de copiar la regla, y si la consulta falla sigue con un aviso (salvo que sin ese dato no se pueda armar el comprobante). Lo que no se puede consultar se copia citando el código y el manual, en [validation-rules](validation-rules.md#de-dónde-sale-cada-regla) y en un comentario donde se aplica, y `yarn test:arca` manda el caso límite a ARCA testing para ver que lo sigue rechazando. Ya consultan:
  - el último número autorizado (`FECompUltimoAutorizado`, y `FEXGetLast_CMP` y `FEXGetLast_ID` en la `E`), en vez de numerar localmente;
  - el padrón (`arcli padron` y el IVA receptor automático con `consultarPadron`);
  - la cotización oficial (`FEParamGetCotizacion`, y `FEXGetPARAM_MON_CON_COTIZACION` en la `E`): la que va con `--misma-moneda` y la que se compara con `--cm` (10119). Con una fecha pasada y `--misma-moneda` se pide con `FchCotiz`, que el SDK no manda: `ArcaBillingGateway` llama al método con `genericService` de `@arcasdk/core`;
  - el asociado de una nota (`FECompConsultar`, y `FEXGetCMP` en la `E`): que exista, el tope de la NC, la fecha de una nota FCE, que una nota FCE coincida con él en moneda, receptor y fecha, y los datos que hereda una nota `E`;
  - el estado del asociado de una nota FCE de anulación en el Registro de FCE (`wsfecred`, `consultarHistorialEstadosComprobante`);
  - el régimen FCE del receptor (`wsfecred`, `consultarMontoObligadoRecepcion`, con `verificarFce`);
  - los permisos de embarque de la `E` (`FEXCheck_Permiso`);
  - las tablas de WSFEX: países, CUIT de países, monedas, unidades, incoterms, idiomas y actividades.
    Siguen copiadas, porque ARCA no tiene cómo preguntarlas antes de emitir: la ventana de fechas, el IVA receptor por letra (`FEParamGetCondicionIvaReceptor` existe, pero en testing su tabla no coincide con lo que ARCA acepta: marca consumidor final solo para `C`, y la del manual también para `B`), el documento del receptor por letra y en FCE, y los ids de alícuota, que `yarn test:arca` compara con las tablas de ARCA.
- **CLI primero.** El flujo principal se piensa desde la terminal; el modo interactivo es una capa encima y no agrega comandos de emisión.
- **Una sola ruta de validación.** El asistente arma `BillingCommandInput` y pasa por `BillingService`, igual que los flags: mismas validaciones, vista previa y emisión.
- **Wizard, no pantalla completa.** Prompts encadenados con `@inquirer`.
- **`testing` por defecto.** Con la config por defecto, emitir en producción pide `--produccion` y además `--emitir` o confirmar en la terminal. Quien guarda `entorno produccion` y `emitir true` emite sin flags: es a propósito.
- **Todo visible.** Lo que ARCLI envía a ARCA se puede ver en la vista previa, en `--json` o en `--bruto`.
- **`FECompConsultar` sin el mapeo del SDK (SDK-13).** `getVoucherInfo` de `@arcasdk/core` descarta los asociados, el período de servicio, el vencimiento del pago, `CanMisMonExt`, las alícuotas, los tributos, los opcionales y las observaciones. `ArcaVoucherHistoryGateway.getVoucher` llama al método con `genericService` y mapea la respuesta entera, así `consultar`, `ultimos`, el historial del modo interactivo y la consulta del asociado de una nota usan la misma. Sin `ResultGet` (o con el 602) el comprobante no existe, como en el SDK. Si el SDK los suma, se puede volver a `getVoucherInfo` sin cambiar el `--json`.
- **Lo escrito gana.** Cada dato se resuelve por nivel: el flag del comando, después el JSON de `--cargar` y por último la config. El primer nivel que dice algo decide; solo es error que un mismo nivel pida dos cosas opuestas (por ejemplo `--emitir --previsualizar`).
- **Formato argentino para montos escritos.** Flags, modo interactivo y config usan `src/lib/numbers/argentine-amount.ts`: punto para miles, coma para decimales. El JSON usa números.
- **Fecha argentina.** "Hoy" sale de `toArgentineCalendarDate` (`src/lib/dates/arca-date.ts`), con la zona `America/Argentina/Buenos_Aires`, sin importar la del equipo. Las cuentas de calendario se hacen en un solo sistema (UTC o local), nunca mezclando.
- **Fechas relativas.** `hoy`, `ayer`, `+N`/`-N`, `mes-actual` y `mes-pasado` se resuelven en `src/lib/dates/relative-date.ts` (puro, con la fecha de referencia como parámetro), que reusa los meses de `src/lib/dates/periods.ts`, los mismos de "Este mes" y "El mes pasado" del asistente. Los parsers de la CLI (`billing.command.parser.ts`, `export.command.parser.ts`) los aplican una vez al valor ya mezclado de flag y `--cargar`, y ahí cada campo dice si es un día o una punta de un rango: lo resuelto pasa como `DD/MM/YYYY` y los módulos no saben que hubo una palabra. Las fechas escritas a mano siguen por `parseArgentineDateInputAsArcaDate`, igual que antes.
- **Certificado vencido, antes de ARCA.** `ArcaContextResolver.resolve()` calcula el vencimiento de todos los certificados configurados (`certificateNotices`, con `inspectConfiguredCertificates`; el del entorno activo con el PEM que ya leyó, sin red y una vez por ejecución), porque quien trabaja en testing también tiene que enterarse de que vence el de producción. `certificateExpiry` es solo el del entorno activo. Los comandos los avisan con `resolveArcaRuntime` (`src/cli/arca-runtime.ts`, a stderr) y el modo interactivo en un recuadro bajo la barra. `ArcaClientFactory.create()`, por donde sale todo cliente de ARCA, corta con `CERTIFICATE_EXPIRED` si venció el del entorno activo, antes de pedir el ticket a WSAA; el de otro entorno vencido solo se avisa. `config` no lo avisa por comando: no va a ARCA y `config revisar` ya muestra el vencimiento de los dos entornos.
- **Producción sin DHE.** `servicios1.afip.gov.ar` (WSFE y WSFEX) prefiere DHE con una clave de 1024 bits, que corta con `dh key too small` donde OpenSSL usa `SECLEVEL=2`, como en Debian. `ArcaClientFactory` suma `:!DHE` a `tls.DEFAULT_CIPHERS` al crear un cliente de producción. Ese host pasa a intercambio RSA y pierde forward secrecy; el resto de los hosts negocia ECDHE con y sin el cambio, y se conservan `SECLEVEL` y la validación del certificado. Se descartó `useHttpsAgent` de `@arcasdk/core`: también lo resuelve, pero baja todas las conexiones a `SECLEVEL=1`, acepta DH desde 512 bits, fija TLS 1.2 y habilita la renegociación insegura. `DEFAULT_CIPHERS` es del proceso, así que una sesión que pasa de producción a testing sigue sin DHE; homologación no lo usa. Testing solo no cambia.
- **Links solo de ARCLI.** `sanitizeTerminalText` saca de la salida toda secuencia de la terminal salvo colores, para que un texto de afuera (una observación de ARCA, un error de npm) no mueva el cursor ni tape el aviso de PRODUCCIÓN. Los links (OSC 8) que arma `hyperlink()`/`pathLink()` (`src/ui/primitives/hyperlink.ts`) pasan porque su URL quedó registrada en esa ejecución; uno que venga en un texto de afuera se saca, así no puede mostrar un texto y llevar a otro lado. Solo se usan en terminales conocidas y con colores, y nunca en `--json`.
- **Opciones globales declaradas por comando.** `--testing`, `--produccion`, `--json` y `--bruto` las parsea el programa (están en cualquier comando), pero cada comando declara solo las que usa con los helpers de `src/cli/global-options.ts`; así sale el aviso de opción que no aplica. Si un comando imprime JSON lo decide siempre `resolveOutputJson` (flag o, si no está, la clave `json` de la config).
- **Errores de uso como el resto.** El programa usa `exitOverride()`: commander tira los errores de uso en vez de cortar el proceso y `reportCliError` (`src/cli/error-output.ts`) los imprime como cualquier error. En JSON salen como `INPUT_VALIDATION_ERROR`; en texto, en el mismo panel que el resto de los errores, con la sugerencia de ayuda (commander ya no los escribe: `configureUsageErrors`). Ayuda y versión también pasan por ahí y no son errores.
- **Ante la duda, no duplicar.** Si falla la llamada que emite, no se sabe si ARCA autorizó: `BillingService` lo informa como `EMISSION_UNCERTAIN` con el `arcli ultimos` para verificar, en vez de sugerir reintentar. Por eso `BillingGateway` no usa `createNextVoucher` del SDK sino sus dos pasos: `getNextVoucherNumber` (login en WSAA y último número + 1; si falla no se envió nada y el error sale tal cual) y `createVoucher` (la única llamada que se marca como incierta).
- **El asociado de una nota A, B, C o FCE se consulta una vez, antes de la vista previa.** `executeBillingCommand` lee el asociado con `VoucherHistoryGateway.getVoucher` (`FECompConsultar`) al preparar cada nota (`checkAssociatedInArca`, `src/modules/billing/billing.associated-lookup.ts`), así la vista previa ya muestra el error del tope de la NC y la fecha del asociado de una nota FCE sin `--afecha`. La emisión usa la entrada completada y no vuelve a consultar. Es una llamada más por nota en la vista previa, aceptada para no descubrir el error recién al emitir. `BillingService.execute` no emite una nota FCE sin esa fecha, por si quien llama no la consultó. El modo interactivo ya tiene la factura elegida y no consulta de nuevo. El texto del error del tope es uno solo para A, B, C, FCE y `E` (`creditNoteOverTotalError`). Una nota FCE con `--anulacion` además consulta el estado del asociado en el Registro de FCE (`wsfecred`, `checkFceCancellationInRegistry`), con flags y en el modo interactivo: si el comprador no lo rechazó, ARCA la rechaza con 10154. Es un aviso y no un error, porque el estado puede cambiar antes de emitir y un rechazo de ARCA no emite nada.
- **Permisos de embarque consultados antes de la vista previa.** `ExportService.resolve` pasa cada permiso de la `E` por `FEXCheck_Permiso` (`ExportGateway.checkPermit`, una lectura) con el destino ya resuelto (`src/modules/export/export.permits.ts`). Si ARCA contesta `NO` corta con `INPUT_VALIDATION_ERROR`: la respuesta es inequívoca y `FEXAuthorize` rechazaría el comprobante. Si la consulta falla o el estado no es `OK` ni `NO`, sigue con un aviso: una caída de ese método no tiene que frenar una emisión que puede estar bien. En testing ARCA contesta `OK` a cualquier permiso, así que la vista previa dice "OK en testing" y no "válido".
- **`factura <letra>` comparte un comando para A, B, C y E.** La familia registra los flags de facturación y, ocultos, los de la `E` (`registerExportOptions` devuelve los que agregó). Los que se pasaron por línea de comandos y no aplican a la letra elegida se saltean con un aviso (`src/cli/skipped-options.ts`) en lugar de cortar. Los atajos (`fa`, `fe`…) registran solo los suyos y siguen siendo estrictos.
- **WSFEX no lanza.** `FEXAuthorize` devuelve `FEXResultAuth` o `FEXErr` en vez de tirar error: `src/modules/export/export.response.ts` lo normaliza al mismo `estado` de A/B/C, así que un rechazo es un resultado válido con exit code `2` y no un error del comando. WSFEX numera por punto de venta y tipo, y `FEXGetLast_CMP` lleva el punto de venta y el tipo dentro de `Auth`. `@arcasdk/core` arma `{ Auth: {Token, Sign, Cuit}, ...params }`, así que un `Auth` propio pisa el suyo: `ArcaClientFactory.createExportGateway` le da al gateway un autenticador (`AuthRepository` del SDK, con el mismo almacenamiento de tickets) y el gateway manda el `Auth` completo, con token y firma (ralcorta/arcasdk#238 lo arregla en el SDK y sigue abierto). El ID de solicitud sale de `FEXGetLast_ID`. Los ítems se validan contra `--monto` antes de WSAA (`assertExportItemsTotal`): el manual de WSFEX v3.1.0 lo lista como control (1610), y validarlo antes evita autenticar en WSAA un total que no cierra.
- **Categorías del monotributo desde una página web, con respaldo incluido.** ARCA no publica las categorías en un web service ni en un archivo para bajar: están en una tabla HTML de `afip.gob.ar/monotributo/categorias.asp`. `src/modules/monotributo/monotributo.parser.ts` la lee sin parser de HTML (expresiones sobre una tabla simple, sin sumar dependencias) y `checkMonotributoTable` descarta cualquier lectura rara: 11 filas de la A a la K, topes que crecen y cuotas que son la suma de impuesto integrado, SIPA y obra social. Lo leído se guarda en `monotributo.json` junto a la config con la fecha de consulta. Se consulta la primera vez (una sola: si falla, no se reintenta en cada ejecución) y después solo con `--actualizar`, porque ARCA cambia la tabla dos veces por año; el aviso de tabla vieja (pasó el 1/2 o el 1/8 y la vigencia es anterior) avisa cuándo conviene. El paquete trae una copia (`monotributo.bundled.ts`, se actualiza a mano en las releases de febrero y agosto con `yarn monotributo:tabla`): se usa sin conexión, si la página cambió o si es más nueva que la guardada. La categoría propia sale del padrón una vez por CUIT y entorno, y si falla no se marca nada: la tabla nunca depende del certificado.
