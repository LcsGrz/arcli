# Arquitectura

Cómo está organizado el código de ARCLI y dónde tocar para extenderlo. Pensado para contributors; para usar el CLI no hace falta.

Stack: TypeScript estricto (ESM), Node.js, [commander](https://github.com/tj/commander.js), [zod](https://zod.dev), [`@arcasdk/core`](https://github.com/ralcorta/arcasdk) para hablar con ARCA, `conf` para la configuración persistente y `@inquirer` para el modo interactivo.

## Flujo de una emisión

```text
src/cli (commander)
  -> parseo de flags y carga del JSON (--cargar)
  -> src/modules/billing: mezcla flags > JSON > config > defaults, valida, arma la solicitud
  -> src/services/arca: gateway contra ARCA (emite con --emitir; la vista previa también consulta: padrón, cotización, tablas de WSFEX)
  -> src/modules/pdf + src/services/pdf: PDF opcional, después de emitir
  -> presenter del módulo (billing.presenter.ts) con los paneles de src/ui (o JSON)
```

Entre el parseo y la vista previa, `prepareBillingInput` (`src/modules/billing/billing.prepare.ts`) completa la condición IVA desde el padrón, pide la cotización oficial si hace falta y junta los avisos de la entrada. La usan los comandos con flags y el modo interactivo, así que los dos preparan la emisión igual. El régimen FCE se consulta aparte, con el lote ya validado (`resolveFceWarningsInOrder`). `executeBillingCommand` recibe la config y los gateways como dependencias, para testear el comando entero con un ARCA falso (`billing.command.execute.test.ts`).

La factura de exportación `E` y sus notas recorren el mismo camino con otro módulo y otro gateway: `src/modules/export` (mezcla, validación de ítems y armado del `Cmp` de WSFEX) y `src/services/arca/arca-export.gateway.ts` (`wsfex`), porque WSFEX tiene otro contrato que `wsfe`.

El comportamiento visible de cada paso está en el [modelo mental](mental-model.md).

## Núcleo y adaptadores

El núcleo (`modules` y `lib`) tiene casos de uso puros que no saben quién los llama: el CLI con flags, el asistente y, en la 3.0, `arcli mcp` y `arcli servir`. Devuelven datos, no texto de pantalla; cada adaptador decide cómo mostrarlos. El motivo es la paridad entre superficies, lo que más veces faltó: REV-50 a REV-53 existen porque cada superficie tenía su propio camino.

- **Puertos solo donde hay dos implementaciones reales**, contando el fake de los tests: ARCA (los gateways), `Clock` y `TicketStore`. `IdempotencyStore` recién con `arcli servir`. El PDF, la config y el logger quedan como están hasta que aparezca una segunda implementación.
- **Errores con `AppError`** y excepciones, como hasta ahora. No hay un `Result` propio.
- **El JSON es un objeto hasta el borde (REV-49).** Cada módulo tiene su `serialize…`, que devuelve el objeto del contrato y no texto; el objeto o array de una facturación lo decide `serializeBillingOutput`. El único `JSON.stringify` de la salida es `renderJson`, adentro de `writeTerminalJson` y `writeTerminalJsonError`. Así `arcli mcp` y `arcli servir` usan las mismas formas sin volver a parsear. `serialize…` puede traer claves en `undefined`: en el JSON no salen.
- **El error también.** `serializeError` (`src/lib/errors/serialize-error.ts`) devuelve `{ codigo, detalles, error, sugerencia }` de cualquier error, y los de zod los describe antes billing (`describeSchemaError`). `src/ui` solo arma el panel.
- **Códigos de error en una lista (ARQ-3).** `AppError` y sus subclases solo aceptan un `ErrorCode`, que sale de `ERROR_CODES` (`src/lib/errors/error-codes.ts`): uno que no está no compila. Los `detalles` se tipan solo donde la forma es fija (el lote, `EMISSION_UNCERTAIN` y `codigoCausa`).
- **Sin capa de entidades de dominio ni mappers por capa.** La única traducción a los tipos del SDK vive en `services/arca` (ARQ-4).
- **Tipos propios para emitir (ARQ-4).** La solicitud es `VoucherRequest` (`modules/billing/voucher-request.ts`; en la `E`, `ExportVoucherPayload`), con los nombres de ARCA porque es lo que sale en `solicitud`. El gateway la pasa al SDK sin copiarla, y el tipo `SdkRequest` hace que un campo que el SDK no tiene no compile. La respuesta es `AuthorizationAnswer` (`modules/billing/authorization-answer.ts`): `services/arca` busca cada dato en lo que devuelve el SDK y lo entrega como vino, sin convertirlo, con `raw` para `--bruto`; qué quiere decir (si se emitió, se rechazó o no se sabe) lo deciden `billing-response` y `export.response`. Buscarlo es parte de la llamada: si falla, es `EMISSION_UNCERTAIN`. Los datos que no siempre hacen falta son getters, para que uno ilegible que no se usa no cueste el CAE. `cli` recibe el cliente como `ArcaClient`, sin conocer el SDK.
- **Consultas separadas de emisiones:** una operación que lee no emite, y la que emite no se reintenta a ciegas.
- **Sin Effect-TS** ni otro runtime de efectos.

Las fronteras las hace cumplir ESLint (ver [Reglas de dependencia](#capas)). Lo que hoy no se cumple está en `warn` con el ticket que lo cierra: es deuda, no un patrón para copiar.

Descartado:

- Un `Result` propio en vez de excepciones: mucho cambio en todo el código sin un problema que resuelva hoy.
- Puertos para todo (PDF, config, logger, sistema de archivos): interfaces con una sola implementación que no aportan y hay que mantener.
- La arquitectura hexagonal de libro (entidades, mappers y DTO por capa, una carpeta por anillo): más ceremonia que la que pide un CLI de este tamaño; se toma solo la idea de que el núcleo no conoce a sus adaptadores.

Reglas de dependencia:

- La lógica de negocio vive en `modules/`, nunca en `cli/`.
- Solo `services/` conoce `@arcasdk/core`. Los tipos del SDK se importan de `src/services/arca/arca-sdk.types.ts`, y solo dentro de `services/arca`: afuera van los tipos propios y `ArcaClient` (`arca-client.factory.ts`). Es el único archivo que puede usar una ruta interna (`@arcasdk/core/lib/...`): la raíz del SDK no exporta los tipos del comprobante de wsfe, y si una versión los mueve se arregla ahí.
- `src/ui` no importa `modules`, `services` ni `cli`. Lo que depende del dominio, como las etiquetas de los campos en un error de zod, lo describe el módulo y `cli` lo une (`formatCliError` para el panel y `serializeCliError` para el JSON, en `cli/error-output.ts`).
- `lib`, `modules` y `services` importan la UI desde sus barrels (`ui/primitives`, `ui/components`, `ui/presenters`, `ui/stream`, `ui/theme`), nunca desde `src/ui`: ese barrel reexporta todo y arma ciclos. `cli` puede usar `src/ui`. Dentro de `src/ui`, imports directos entre archivos.
- El núcleo (`modules` y `lib`, sin tests) no importa `cli`, `services`, `@inquirer/*`, `commander`, `ora` ni `node:process` (error), ni `ui/*`, `conf` ni `node:fs` (warn; lo cierran ARQ-7 para `ui/*` y ARQ-12 para `conf` y `node:fs`), y no lee `process` (error, salvo `restrict-to-owner.ts`, `certificate-store.ts` y `config.service.ts`, en warn hasta ARQ-12: la app pasa la plataforma como parámetro) ni el reloj (`new Date()` sin argumentos, `Date.now`; error: las funciones reciben la fecha y los servicios, el puerto `Clock`, que leen en cada operación). `services` no importa `cli` (error). Los módulos que son de la app (`completion`, `desktop-shortcut`, `examples`, `storybook`, `update-check`) tienen esa misma deuda, y además `process`, `node:process` y el reloj, en warn con el mensaje de ARQ-7, que los muda.
- ESLint hace cumplir todas las reglas anteriores (`no-restricted-imports` lo que ya es error; `no-restricted-syntax` el reloj y `no-restricted-globals` `process`, error en el núcleo y warn en las excepciones del punto anterior; `@typescript-eslint/no-restricted-imports` la deuda en warn), y dependency-cruiser, que no haya ciclos. El lint con tipos de `src/` suma `no-floating-promises`, `no-explicit-any` y `switch-exhaustiveness-check` en error (también con `default`: cada caso de una unión con nombre, para que uno nuevo falle donde no se maneja), y `max-lines` (400 líneas de código y 800 de tests, sin blancos ni comentarios) en warn.

## El plugin de PDF

`@arcasdk/pdf` renderiza con Puppeteer y descarga un navegador, así que **no es dependencia de ARCLI**. Se instala con `npm install --ignore-scripts` en `<carpeta de config>/plugins/pdf` y se carga con `createRequire` (`src/services/pdf/pdf-plugin.ts`). ARCLI fija una versión del plugin; si cambia, `arcli pdf` lo avisa. Comportamiento para usuarios: [PDF de comprobantes](pdf.md).

## Cómo extender

### Agregar un comprobante

Dentro del alcance del proyecto (A, B y C de factura, nota de crédito y débito, sus versiones FCE y Recibo A, B y C):

1. Definilo en `src/modules/billing/voucher-kind-map.ts` (`VOUCHER_KIND_MAP`): tipo ARCA, familia, letra y si requiere comprobante asociado.
2. Los comandos se registran solos desde ese mapa (`registerBillingShortcutCommands` y `registerBillingFamilyCommands`).
3. Si cambia una regla de negocio, ajustala en `src/modules/billing/`.
4. Actualizá tests y docs ([cli-reference](cli-reference.md), [validation-rules](validation-rules.md)).

La letra `E` no pasa por `VOUCHER_KIND_MAP`: WSFEX tiene otro contrato (autorización que no lanza, ítems, país de destino, tablas propias), así que vive en `src/modules/export/` con sus propios tipos (`EXPORT_VOUCHER_KIND`, `EXPORT_CREDIT_NOTE_KIND`, `EXPORT_DEBIT_NOTE_KIND`) y su gateway. Las notas `E` consultan su asociado con `FEXGetCMP` (`ExportGateway.getVoucher`, una lectura) antes de armar el `Cmp`: toman de ahí cliente, destino y moneda, y lo comparan con las reglas que ARCA aplica contra el asociado (`src/modules/export/export.notes.ts`). A diferencia de `FEXGetLast_CMP`, `FEXGetCMP` lleva el `Cmp` fuera de `Auth`, así que el SDK no lo rompe.

### Agregar una clave de configuración

1. Sumala a `configPublicKeySchema` y al esquema en `src/modules/config/config.schemas.ts`.
2. Mapeala en `config-keys.ts` y validala en `config-value-parser.ts`.
3. Ubicala en una sección y ponele nombre en `config.sections.ts`: de ahí salen el orden de `arcli config` y de "Modificar configuración" (un test exige que cada clave esté en una sola sección). Agregá cómo se muestra su valor en `config.presenter.ts`.
4. Documentala en [configuración](configuration.md) y, si el modo interactivo la expone, en `src/modules/interactive/config-fields.ts`.

### Extender el asistente

Las piezas están en "El navegador del asistente", en [Decisiones de diseño](#decisiones-de-diseño). Lo que se agrega en cada caso:

- **Un opcional** (A, B, C o `E`): una entrada en su catálogo, [`billing-optionals.ts`](../src/modules/interactive/billing-optionals.ts) o [`export-optionals.ts`](../src/modules/interactive/export-optionals.ts), con `available`, `describe`, `owns` (los campos que son suyos: vuelven al valor inicial si se desmarca) y `steps`. Sus preguntas van en [`advanced-options.ts`](../src/cli/interactive/advanced-options.ts) o [`export-options.ts`](../src/cli/interactive/export-options.ts). Si su valor inicial sale de algo que puede cambiar (la factura que se repite), `resetWhen`. Si en un contexto es obligatorio, `required` con el motivo y un `requiredOptional` en el flujo, donde ya se sabe.
- **Una pregunta:** un paso que pregunta una sola cosa, arranca con `previous`, declara en `dependsOn` los pasos de los que lee algo y en `writes` los campos que escribe. Si el dato ya tiene fábrica (receptor, monto, moneda, fecha, CBU, consumidor final, datos de la `E`), se usa la de [`steps/`](../src/cli/interactive/steps/) con un `Lens` sobre el estado del flujo.
- **Una regla entre campos:** en `BILLING_RULES` ([`billing.rules.ts`](../src/modules/billing/billing.rules.ts)) o `EXPORT_RULES` ([`export.rules.ts`](../src/modules/export/export.rules.ts)), con sus `fields`, el texto del CLI y `question` si ese texto nombra flags. El CLI la corre con `assertRules` donde resuelve esos campos; el asistente, con `ruleValidator` en cada pregunta que escribe uno y en el `finalize` del flujo. El test de reglas del asistente al azar falla si un campo no lo valida ninguna pregunta.
- **Un flujo:** su `*.flow.ts`, un `*-input.ts` puro que arma la entrada del CLI con lo respondido (de ahí salen la solicitud, el comando equivalente y la entrada de las reglas), su `finalize` con las reglas, una entrada en `FLOWS` de [`navigator.property.test.ts`](../src/cli/interactive/__tests__/navigator.property.test.ts) y sus golden de pantallas.

### Cambiar el contrato

Comandos, flags, claves de config y JSON son contrato público. Antes de cambiarlos, mirá [CONTRIBUTING](../CONTRIBUTING.md#contrato-del-cli) y actualizá [entrada y salida](input-output.md) y los tests de serialización.

## Decisiones de diseño

- **Docs con una sola fuente.** El sitio (`site/`, Starlight) genera sus páginas desde `docs/` en cada build en vez de mover los archivos: los links de GitHub que ya circulan siguen andando, los tests de docs leen lo mismo y nadie edita dos copias. Ver [Sitio de documentación](development.md#sitio-de-documentación).
- **Una página por comprobante, generada.** Las opciones de cada comprobante se repiten mucho entre páginas (monto, concepto, receptor, al ejecutar). `scripts/docs/comprobantes.ts` las tiene una sola vez, con su largo, su corto y qué es, y la lista de cada comprobante; las condiciones IVA por letra salen de `listAllowedIvaConditions`. `yarn docs:comprobantes` escribe `docs/comprobantes/*.md` (tablas que se leen en GitHub) y el sitio dibuja cada opción como tarjeta con los comentarios `<!-- arcli: ... -->`. `scripts/docs/comprobantes-docs.test.ts` falla si los `.md` quedaron viejos, si un flag del CLI no está o si se nombra uno que no existe. Se descartó leer los textos de la ayuda de commander: son para la terminal y no explican cada valor.
- **Íconos del README, del sitio.** Los títulos `##` del README llevan los dibujos de `site/src/icons.ts` como SVG sueltos en `docs/assets/iconos/` (GitHub no deja SVG en línea ni `style`), con trazo celeste `#2f86c9` fijo, que se ve sobre el fondo claro y el oscuro de GitHub. `yarn docs:readme-iconos` los escribe y pone cada título con su `<img>` y un `<a id>` con el ancla de antes (con el ícono, GitHub generaría `#-empezar`); `scripts/docs/readme-iconos.test.ts` falla si se desincronizan. El sitio no publica el README, así que no le llegan los `<img>`.

- **Consultar antes que copiar.** Una regla de ARCA copiada en ARCLI queda vieja en silencio: si ARCA la afloja, ARCLI sigue bloqueando algo válido. Cuando ARCA tiene un método de consulta, la vista previa le pregunta en lugar de copiar la regla, y si la consulta falla sigue con un aviso (salvo que sin ese dato no se pueda armar el comprobante). Lo que no se puede consultar se copia citando el código y el manual, en [validation-rules](validation-rules.md#de-dónde-sale-cada-regla) y en un comentario donde se aplica, y `yarn test:arca` manda el caso límite a ARCA testing para ver que lo sigue rechazando. Ya consultan:
  - el último número autorizado (`FECompUltimoAutorizado`, y `FEXGetLast_CMP` y `FEXGetLast_ID` en la `E`), en vez de numerar localmente;
  - el padrón (`arcli padron` y el IVA receptor automático con `consultarPadron`);
  - la cotización oficial (`FEParamGetCotizacion`, y `FEXGetPARAM_MON_CON_COTIZACION` en la `E`): la que va con `--misma-moneda` y la que se compara con `--cm` (10119). Con una fecha pasada y `--misma-moneda` se pide con `FchCotiz`, que el SDK no manda: `ArcaBillingGateway` llama al método con `genericService` de `@arcasdk/core`;
  - el asociado de una nota (`FECompConsultar`, y `FEXGetCMP` en la `E`): que exista, el tope de la NC, la fecha de una nota FCE, que una nota FCE coincida con él en moneda, receptor y fecha, y los datos que hereda una nota `E`;
  - el estado del asociado de una nota FCE de anulación en el Registro de FCE (`wsfecred`, `consultarHistorialEstadosComprobante`);
  - el régimen FCE del receptor (`wsfecred`, `consultarMontoObligadoRecepcion`, con `verificarFce`);
  - los permisos de embarque de la `E` (`FEXCheck_Permiso`);
  - las tablas de WSFEX: países, CUIT de países, monedas, unidades, incoterms, idiomas y actividades.
    Siguen copiadas, porque ARCA no tiene cómo preguntarlas antes de emitir: la ventana de fechas, el IVA receptor por letra (`FEParamGetCondicionIvaReceptor` existe, pero en testing su tabla no coincide con lo que ARCA acepta: marca consumidor final solo para `C`, y la del manual también para `B`), el documento del receptor por letra y en FCE, y los ids de alícuota, que `yarn test:arca` compara con las tablas de ARCA.
- **CLI primero.** El flujo principal se piensa desde la terminal; el modo interactivo es una capa encima y no agrega comandos de emisión.
- **Una sola ruta de validación.** El asistente arma `BillingCommandInput` y pasa por `BillingService`, igual que los flags: mismas validaciones, vista previa y emisión.
- **Wizard, no pantalla completa.** Prompts encadenados con `@inquirer`.
- **Una pregunta por paso (REV-60).** El motor de pasos (`runWizard` en `src/modules/interactive/wizard.ts`) guarda la última respuesta de cada paso, por nombre, y se la pasa al paso (`run(state, { previous })`) para que arranque marcada o escrita. Al volver restaura el estado de antes del paso. Un paso declara en `dependsOn` los pasos anteriores de los que lee algo para preguntar (el texto, las opciones, la marcada por defecto o la validación); si la respuesta de uno cambia (o, con `{ step, fields }`, uno de esos campos, como si falta el CUIT del país para el ID impositivo de la `E`), se olvidan las de los pasos que dependen de él, también de forma indirecta, y los demás siguen ofreciendo la suya (REV-65). Lo recordado igual pasa por la validación del paso, y una lista arranca en su opción por defecto si lo recordado ya no está entre las opciones (`availableChoice`). Por eso un paso hace una sola pregunta: dos preguntas en un paso harían que "Volver" desde la segunda saltara la primera. Los opcionales de A, B, C y `E` son un grupo que corre un `runWizard` anidado y comparte las respuestas entre vueltas a la selección: la selección muestra lo respondido de los opcionales completos, y con Enter cada vuelta arranca de los valores iniciales, así lo de un opcional desmarcado no llega al comprobante (ver "El navegador del asistente", abajo).
- **El navegador del asistente.** Cada flujo del asistente (factura, nota, "Repetir" y sus versiones de la `E`) armaba a mano los opcionales, las reglas entre campos, la entrada final y las preguntas comunes, y un arreglo en una familia quedaba roto en otra: lo desmarcado llegaba a la `E`, "Volver" perdía los opcionales, la vista previa rechazaba lo que las preguntas aceptaban y el comando equivalente salía de otra fuente que la solicitud. Ahora cada patrón está una vez en `src/modules/interactive/` (lógica, sin `@inquirer`) y `src/cli/interactive/` solo pregunta:
  - **El motor** ([`wizard.ts`](../src/modules/interactive/wizard.ts)). Cada paso recibe `run(state, { previous, memo, error, failedFields })`. `memo` es lo que recuerda además de su respuesta y se olvida con ella. `writes` son los campos que escribe, fijos o según lo respondido. `auto` escribe sin preguntar ni entrar en la historia y `memoOf` usa el memo de otro paso. `finalize` corre al final: si falla, vuelve al paso que escribe el campo, con el error. `resume` retoma en ese paso con un error de afuera. Un dato que se compara con otro que se elige después (el período de una nota o la fecha de pago de la `E` contra la fecha del comprobante, que está en los opcionales) se controla al preguntar contra el extremo más permisivo que acepta ARCA, y exacto en la pregunta posterior y en `finalize`. `confirm` corre después de `finalize` y es la vista previa con "¿Emitimos?" (`emissionStep` en `session.ts`): si devuelve BACK (Esc), el asistente vuelve a la última pregunta respondida con todo lo respondido, en vez de terminar (TUI-15).
  - **El grupo de opcionales** ([`optional-group.ts`](../src/modules/interactive/optional-group.ts)). `optionalGroup` es la selección más las preguntas de cada opcional, con lo marcado y lo respondido en su memo. `composeOptionals`, pura, arma el resultado: lo inicial más los `owns` de lo marcado, disponible y completo, en el orden del catálogo. `resetWhen` hace que un opcional olvide lo suyo cuando cambia de dónde sale. `requiredOptional` pide como paso propio, con el motivo, un opcional que en ese contexto es obligatorio, como el consumidor final desde el tope de la RG 5700/2025.
  - **Las reglas únicas** ([`src/lib/rules/rules.ts`](../src/lib/rules/rules.ts)). `BILLING_RULES` y `EXPORT_RULES` las corre el CLI con `assertRules` y el asistente con `ruleValidator` al preguntar y en `finalize` ([`rule-validator.ts`](../src/modules/interactive/rule-validator.ts)), con el mismo texto (o el de la pregunta, si el del CLI nombra flags). Lo que sabe ARCA (padrón, cotización, tablas) no es regla local. Las reglas de la `E` que usan constantes de otro módulo viven en ese módulo, para no armar ciclos.
  - **Una sola salida.** Cada flujo tiene un `*-input.ts` puro ([`invoice-input.ts`](../src/modules/interactive/invoice-input.ts), [`note-input.ts`](../src/modules/interactive/note-input.ts), [`export-input.ts`](../src/modules/interactive/export-input.ts), [`export-note-input.ts`](../src/modules/interactive/export-note-input.ts), [`export-repeat-input.ts`](../src/modules/interactive/export-repeat-input.ts)) que arma la entrada del CLI. De esa entrada salen la solicitud (`prepareBillingInput`), el comando equivalente y la entrada de las reglas, así el equivalente no lleva nada que no se respondió, como la cotización oficial en `--cm`. Las fechas se guardan completas (`completeDateInput`).
  - **La biblioteca de pasos.** Receptor, monto, moneda, fechas, CBU, consumidor final y los datos de la `E` son fábricas en [`src/cli/interactive/steps/`](../src/cli/interactive/steps/), con su lógica en [`src/modules/interactive/steps/`](../src/modules/interactive/steps/). Cada una lee y escribe el estado del flujo con un `Lens` y declara `writes`. "Repetir" traba la moneda con `CurrencyLock`.

  Cómo agregar un opcional, una pregunta, una regla o un flujo: [Extender el asistente](#extender-el-asistente). La red de tests es genérica:
  - los golden de pantallas ([`screens.golden.test.ts`](../src/cli/interactive/__tests__/screens.golden.test.ts), en `__golden__/pantallas/`) fijan lo que se ve en cada flujo;
  - el asistente al azar ([`navigator.property.test.ts`](../src/cli/interactive/__tests__/navigator.property.test.ts), fast-check con semillas fijas) recorre cada flujo con "Volver", selecciones y textos al azar, y controla cinco invariantes: (1) la vista previa acepta lo que aceptan las preguntas, (2) el comando equivalente arma la misma solicitud, (3) lo de un opcional desmarcado no llega a la entrada, (4) al volver, la selección y las preguntas arrancan con lo marcado y lo escrito, y (5) todo valor final pasó por el validador de su pregunta;
  - el test de reglas del mismo archivo exige que cada campo de una regla que aplica lo valide una pregunta con las reglas del flujo y lo escriba un paso.

  Descartado:
  - Los `writes` del grupo como la unión fija de los `owns`: `finalize` volvería al grupo por un campo de un opcional desmarcado. El grupo escribe los de lo marcado.
  - Un tipo aparte para el dato que a veces es obligatorio: `OptionalDef` extiende `FieldDef`, así `label`, `describe` y `owns` se declaran una vez. Un dato obligatorio fuera de un grupo no tiene paso propio: hoy no hay ninguno.
  - Componer en el orden en que se marcó: el resultado dependería de cómo se eligió. Se compone en el orden del catálogo.
  - Un paso con todas las preguntas de un dato obligatorio: "Volver" saltaría preguntas. `requiredOptional` hace un paso por pregunta.
  - Escalar el exento y el no gravado en "Repetir" con otro monto: se vuelven a preguntar, con el opcional preseleccionado.
  - Arrancar "En pesos" siempre con la cotización oficial: si el CLI tomaría la `cotizacion` de la config sin `--cm`, arranca con esa, así dejarla sin tocar hace lo mismo que el CLI.
  - Preguntas declarativas, cambiar `@inquirer` y rediseñar la carga de ítems de la `E`, que sigue como bucle propio dentro de un paso, con su memo: ninguna falla lo pedía.

- **`testing` por defecto.** Con la config por defecto, emitir en producción pide `--produccion` y además `--emitir` o confirmar en la terminal. Quien guarda `entorno produccion` y `emitir true` emite sin flags: es a propósito.
- **Todo visible.** Lo que ARCLI envía a ARCA se puede ver en la vista previa, en `--json` o en `--bruto`.
- **`FECompConsultar` sin el mapeo del SDK (SDK-13).** `getVoucherInfo` de `@arcasdk/core` descarta los asociados, el período de servicio, el vencimiento del pago, `CanMisMonExt`, las alícuotas, los tributos, los opcionales y las observaciones. `ArcaVoucherHistoryGateway.getVoucher` llama al método con `genericService` y mapea la respuesta entera, así `consultar`, `ultimos`, el historial del modo interactivo y la consulta del asociado de una nota usan la misma. Solo el 602 es que el comprobante no existe: `genericService` no mira `Errors`, así que el gateway los lee, y otro error o una respuesta sin los datos del comprobante es `ARCA_VOUCHER_QUERY_ERROR` (ERR-1), porque con esta consulta se verifica una emisión incierta. La `E` hace lo mismo con el 1020 (ERR-15): sin los datos mínimos (número, tipo de exportación que conocemos y moneda) es `ARCA_VOUCHER_QUERY_ERROR`. Si vino con el número pedido y su CAE, existe pero no se entiende: `consultar` falla igual, con un texto que lo dice, y las listas lo saltean con un aviso (`VoucherQueryError.exists`). A diferencia del SDK (`isAfipNotFoundError`), una excepción con "no existe" en el texto no cuenta. Si el SDK los suma, se puede volver a `getVoucherInfo` sin cambiar el `--json`.
- **Lo escrito gana.** Cada dato se resuelve por nivel: el flag del comando, después el JSON de `--cargar` y por último la config. El primer nivel que dice algo decide; solo es error que un mismo nivel pida dos cosas opuestas (por ejemplo `--emitir --previsualizar`).
- **Formato argentino para montos escritos.** Flags, modo interactivo y config usan `src/lib/numbers/argentine-amount.ts`: punto para miles, coma para decimales. El JSON usa números.
- **Fecha argentina.** "Hoy" sale de `toArgentineCalendarDate` (`src/lib/dates/arca-date.ts`), con la zona `America/Argentina/Buenos_Aires`, sin importar la del equipo. Las cuentas de calendario se hacen en un solo sistema (UTC o local), nunca mezclando.
- **Fechas relativas.** `hoy`, `ayer`, `+N`/`-N`, `mes-actual` y `mes-pasado` se resuelven en `src/lib/dates/relative-date.ts` (puro, con la fecha de referencia como parámetro), que reusa los meses de `src/lib/dates/periods.ts`, los mismos de "Este mes" y "El mes pasado" del asistente. Quien mezcla flags y `--cargar` (`resolveBillingInput`, en `src/modules/billing/billing.input.ts`, y `export.command.parser.ts` en la E) los aplica una vez al valor ya mezclado, con una sola lectura del reloj por comando, y ahí cada campo dice si es un día o una punta de un rango: lo resuelto pasa como `DD/MM/YYYY` y lo que sigue no sabe que hubo una palabra. Las fechas escritas a mano siguen por `parseArgentineDateInputAsArcaDate`, igual que antes.
- **El perfil de ARCA no sabe quién lo pide.** `src/modules/config/arca-profile.ts` define `ArcaProfile` y las reglas puras (entorno, CUIT y rutas de las credenciales); `loadArcaProfile` lee los PEM y arma el contexto a partir de una config ya leída, sin flags, salida ni `ConfigService`. Los flags, `--json`, los permisos de las carpetas y el aviso los suma la app en `src/cli/arca-runtime.ts` (`CliArcaRuntime`). El contexto es un tipo propio (`ArcaContext`), para que el núcleo no conozca el del SDK.
- **Los tickets de WSAA van a disco, salvo que se pida otra cosa.** `ArcaClientFactory` acepta un `ticketStorage` del SDK (por ejemplo, `MemoryTicketStorage`), que usan el cliente y el autenticador de WSFEX. Los del SDK fijan el CUIT y el entorno al construirse, así que va una fábrica por CUIT y entorno; sin `ticketStorage`, van al `ticketPath` del perfil, como siempre.
- **Certificado vencido, antes de ARCA.** `loadArcaProfile` (`src/services/arca/arca-profile.loader.ts`) calcula el vencimiento de todos los certificados configurados (`certificateNotices`, con `inspectConfiguredCertificates`; el del entorno activo con el PEM que ya leyó, sin red y una vez por ejecución), porque quien trabaja en testing también tiene que enterarse de que vence el de producción. `certificateExpiry` es solo el del entorno activo. Los comandos los avisan con `resolveArcaRuntime` (`src/cli/arca-runtime.ts`, a stderr) y el modo interactivo en un recuadro bajo la barra. `ArcaClientFactory.create()`, por donde sale todo cliente de ARCA, corta con `CERTIFICATE_EXPIRED` si venció el del entorno activo, antes de pedir el ticket a WSAA; el de otro entorno vencido solo se avisa. `config` no lo avisa por comando: no va a ARCA y `config revisar` ya muestra el vencimiento de los dos entornos.
- **Producción sin DHE.** `servicios1.afip.gov.ar` (WSFE y WSFEX) prefiere DHE con una clave de 1024 bits, que corta con `dh key too small` donde OpenSSL usa `SECLEVEL=2`, como en Debian. `ArcaClientFactory` suma `:!DHE` a `tls.DEFAULT_CIPHERS` al crear un cliente de producción. Ese host pasa a intercambio RSA y pierde forward secrecy; el resto de los hosts negocia ECDHE con y sin el cambio, y se conservan `SECLEVEL` y la validación del certificado. Se descartó `useHttpsAgent` de `@arcasdk/core`: también lo resuelve, pero baja todas las conexiones a `SECLEVEL=1`, acepta DH desde 512 bits, fija TLS 1.2 y habilita la renegociación insegura. `DEFAULT_CIPHERS` es del proceso, así que una sesión que pasa de producción a testing sigue sin DHE; homologación no lo usa. Testing solo no cambia.
- **Links solo de ARCLI.** `sanitizeTerminalText` saca de la salida toda secuencia de la terminal salvo colores, para que un texto de afuera (una observación de ARCA, un error de npm) no mueva el cursor ni tape el aviso de PRODUCCIÓN. Los links (OSC 8) que arma `hyperlink()`/`pathLink()` (`src/ui/primitives/hyperlink.ts`) pasan porque su URL quedó registrada en esa ejecución; uno que venga en un texto de afuera se saca, así no puede mostrar un texto y llevar a otro lado. Solo se usan en terminales conocidas y con colores, y nunca en `--json`.
- **Opciones globales declaradas por comando.** `--testing`, `--produccion`, `--json` y `--bruto` las parsea el programa (están en cualquier comando), pero cada comando declara solo las que usa con los helpers de `src/cli/global-options.ts`; así sale el aviso de opción que no aplica. Si un comando imprime JSON lo decide siempre `resolveOutputJson` (flag o, si no está, la clave `json` de la config).
- **Errores de uso como el resto.** El programa usa `exitOverride()`: commander tira los errores de uso en vez de cortar el proceso y `reportCliError` (`src/cli/error-output.ts`) los imprime como cualquier error. En JSON salen como `INPUT_VALIDATION_ERROR`; en texto, en el mismo panel que el resto de los errores, con la sugerencia de ayuda (commander ya no los escribe: `configureUsageErrors`). Ayuda y versión también pasan por ahí y no son errores.
- **Una salida rota no corta el trabajo.** `watchOutputs` (`src/cli/closed-output.ts`) escucha el `error` de stdout y stderr: `EPIPE` (alguien la cortó) se ignora y cualquier otro queda anotado sin cortar, porque cortar dejaría un comprobante autorizado sin PDF o un lote a medias. Lo emitido se anota en un registro del proceso (`src/cli/emitted-vouchers.ts`) apenas ARCA responde, y no se pasa por los comandos porque quien avisa es `index.ts`. El aviso (`reportOutputFailure`) y el código salen en `beforeExit`, cuando ya no quedan escrituras pendientes; por eso el CLI no usa `process.exit`. Los errores no esperan a `beforeExit`, porque un socket colgado demoraría `EMISSION_UNCERTAIN`: con JSON esperan a stdout hasta un segundo (`settleOutput`), para que stderr sea un solo documento. El asistente además no pregunta ni emite con stdout roto, y muestra sus errores en stdout si stderr falló (`output-guard.ts` y `show-assistant-error.ts`, en `src/cli/interactive/`).
- **Ante la duda, no duplicar.** Si falla la llamada que emite o de su respuesta no se puede saber si se emitió, no se sabe si ARCA autorizó: `BillingService` (y `ExportService`) lo informa como `EMISSION_UNCERTAIN` con el `arcli ultimos` (en la `E`, `arcli consultar`) para verificar, en vez de sugerir reintentar. Por eso `BillingGateway` no usa `createNextVoucher` del SDK sino sus dos pasos: `getNextVoucherNumber` (login en WSAA y último número + 1; si falla no se envió nada y el error sale tal cual) y `createVoucher` (la única llamada que se marca como incierta). El estado lo decide un solo lugar, `resolveEmissionStatus` (`emission-response.ts`), para A, B, C y la `E` (ERR-20): manda el CAE (con CAE está emitido, aunque haya un error), sin CAE es un rechazo si ARCA contesta `R` o ningún resultado y algún error con código que no es interno, y lo demás (vacía, aprobada sin CAE, rechazada con CAE, errores internos o sin código) es incierto. Los internos son 500, 501 y 502, y en WSFEX también 1000.
- **Se emite lo que mostró la vista previa.** Con la confirmación de "¿Emitimos?", `BillingService.execute` recibe la vista previa confirmada (`preview`) y manda su `payload` tal cual, como `ExportService.execute` con `resolved`: no vuelve a leer el reloj ni a correr las reglas, y solo pide el número. El asistente pasa la de ese intento (`previewAndEmit`; "Volver" arma otra) y los comandos, una por comprobante (`runInteractiveBillingPreview`, alineadas con las entradas). Las reglas que dependen de hoy ya corrieron con el día que se envía; si al confirmar ARCA no acepta la fecha, decide ARCA. El resguardo de la fecha del asociado en una nota FCE se sigue controlando, sobre ese `payload`. Sin pregunta no hay vista previa confirmada y cada comprobante se arma al emitir.
- **El asociado de una nota A, B, C o FCE se consulta una vez, antes de la vista previa.** `executeBillingCommand` lee el asociado con `VoucherHistoryGateway.getVoucher` (`FECompConsultar`) al preparar cada nota (`checkAssociatedInArca`, `src/modules/billing/billing.associated-lookup.ts`), así la vista previa ya muestra el error del tope de la NC y la fecha del asociado de una nota FCE sin `--afecha`. La emisión usa la entrada completada y no vuelve a consultar. Es una llamada más por nota en la vista previa, aceptada para no descubrir el error recién al emitir. `BillingService.execute` no emite una nota FCE sin esa fecha, por si quien llama no la consultó. El modo interactivo ya tiene la factura elegida y no consulta de nuevo. El texto del error del tope es uno solo para A, B, C, FCE y `E` (`creditNoteOverTotalError`). Una nota FCE con `--anulacion` además consulta el estado del asociado en el Registro de FCE (`wsfecred`, `checkFceCancellationInRegistry`), con flags y en el modo interactivo: si el comprador no lo rechazó, ARCA la rechaza con 10154. Es un aviso y no un error, porque el estado puede cambiar antes de emitir y un rechazo de ARCA no emite nada.
- **Permisos de embarque consultados antes de la vista previa.** `ExportService.resolve` pasa cada permiso de la `E` por `FEXCheck_Permiso` (`ExportGateway.checkPermit`, una lectura) con el destino ya resuelto (`src/modules/export/export.permits.ts`). Si ARCA contesta `NO` corta con `INPUT_VALIDATION_ERROR`: la respuesta es inequívoca y `FEXAuthorize` rechazaría el comprobante. Si la consulta falla o el estado no es `OK` ni `NO`, sigue con un aviso: una caída de ese método no tiene que frenar una emisión que puede estar bien. En testing ARCA contesta `OK` a cualquier permiso, así que la vista previa dice "OK en testing" y no "válido".
- **`factura <letra>` comparte un comando para A, B, C y E.** La familia registra los flags de facturación y, ocultos, los de la `E` (`registerExportOptions` devuelve los que agregó). Los que se pasaron por línea de comandos y no aplican a la letra elegida se saltean con un aviso (`src/cli/skipped-options.ts`) en lugar de cortar. Los atajos (`fa`, `fe`…) registran solo los suyos y siguen siendo estrictos.
- **WSFEX no lanza.** `FEXAuthorize` devuelve `FEXResultAuth` o `FEXErr` en vez de tirar error: `src/modules/export/export.response.ts` lo normaliza al mismo `estado` de A/B/C, así que un rechazo es un resultado válido con exit code `2` y no un error del comando. WSFEX numera por punto de venta y tipo, y `FEXGetLast_CMP` lleva el punto de venta y el tipo dentro de `Auth`. `@arcasdk/core` arma `{ Auth: {Token, Sign, Cuit}, ...params }`, así que un `Auth` propio pisa el suyo: `ArcaClientFactory.createExportGateway` le da al gateway un autenticador (`AuthRepository` del SDK, con el mismo almacenamiento de tickets) y el gateway manda el `Auth` completo, con token y firma (ralcorta/arcasdk#238 lo arregla en el SDK y sigue abierto). El ID de solicitud sale de `FEXGetLast_ID`. Los ítems se validan contra `--monto` antes de WSAA (`assertExportItemsTotal`): el manual de WSFEX v3.1.0 lo lista como control (1610), y validarlo antes evita autenticar en WSAA un total que no cierra.
- **Categorías del monotributo desde una página web, con respaldo incluido.** ARCA no publica las categorías en un web service ni en un archivo para bajar: están en una tabla HTML de `afip.gob.ar/monotributo/categorias.asp`. `src/modules/monotributo/monotributo.parser.ts` la lee sin parser de HTML (expresiones sobre una tabla simple, sin sumar dependencias) y `checkMonotributoTable` descarta cualquier lectura rara: 11 filas de la A a la K, topes que crecen y cuotas que son la suma de impuesto integrado, SIPA y obra social. Lo leído se guarda en `monotributo.json` junto a la config con la fecha de consulta. Se consulta la primera vez (una sola: si falla, no se reintenta en cada ejecución) y después solo con `--actualizar`, porque ARCA cambia la tabla dos veces por año; el aviso de tabla vieja (pasó el 1/2 o el 1/8 y la vigencia es anterior) avisa cuándo conviene. El paquete trae una copia (`monotributo.bundled.ts`, se actualiza a mano en las releases de febrero y agosto con `yarn monotributo:tabla`): se usa sin conexión, si la página cambió o si es más nueva que la guardada. La categoría propia sale del padrón una vez por CUIT y entorno, y si falla no se marca nada: la tabla nunca depende del certificado.
